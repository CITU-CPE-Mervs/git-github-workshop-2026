02 / The Problem Slide 3 / 24

What Happens When We Have Group Projects?

In every engineering project (Project X), you have People (Engineers) editing Files/Code. Without version control, your folder looks like this at 2:00 AM:

C:\Users\CpE_Student\Desktop\Project_X\ 3:14 AM
Project_X_v1.zip Oct 12
Project_X_v2_working.zip Oct 18
Project_X_FINAL_pass_na.zip 11:40 PM
Project_X_FINAL_REAL_MERVIN_EDIT_2AM.zip 2:15 AM
Project_X_BROKEN_DONT_DELETE.zip 3:10 AM

"Wait, whose version has the working navbar?"

Sending index_updated(3).html over Messenger or Discord means someone manually copies & pastes lines—and accidentally deletes your code.

"It worked 20 minutes ago, and Ctrl+Z stopped working!"

Once you close your code editor or overwrite a file, your undo history is gone forever.

What Git Solves: History, Safety & Teamwork

You keep one single folder. Git tracks every single change, who made it, when, and why.

03 / Why Not Google Drive? Slide 4 / 24

Why Google Drive & OneDrive Fail for Source Code

Google Drive is great for Word docs and PDFs, but when 3 engineers edit code simultaneously, file-syncing breaks down:

Scenario Google Drive / OneDrive / Zip Git + GitHub
Two people edit index.html at the same time Last person to upload silently overwrites the other, or creates index (Conflicted copy).html. Automatically merges changes on different lines, or highlights exact lines to combine.
Saving a multi-file feature (`index.html` + `style.css` + `app.js`) Syncs files one by one as you type—teammates pull half-finished, broken code mid-sentence. Atomic Commits: Groups all 3 file changes into one named snapshot only when it works.
Experimenting with a risky new idea or AI rewrite You have to duplicate the entire project folder into Copy of Project_X. Branches: Switch to a parallel timeline in 1 millisecond without duplicating folders.
Finding out what broke the app last Tuesday Dig through 15 unnamed zip backups hoping one works. Git Blame & Diff: See the exact line, author, timestamp, and commit message—and revert in 1 click.
Industry Standard: Over 100+ Million developers and virtually every tech company on Earth use Git & GitHub daily. Other VCS: GitLab, Bitbucket, SVN, Perforce
04 / Concept Slide 5 / 24

What is Version Control? (Think Video Game Save Points)

A Version Control System (VCS) is a time machine for your project folder. Every time a feature works, you create a named Commit (Save Point).

Project Timeline (Commit History Graph)
c9ad986 2:15 PM
1. Initial Commit

Starter index.html + example Click Counter works.

4aa3630 2:40 PM
2. Add Contributor Name

Added my name to README.md contributors list.

27ef652 3:00 PM
3. Add Binary Widget

Created widgets/juan.js and hooked into HTML.

UNSAVED 4:35 PM
4. AI Broke Everything!

No panic! Click Discard Changes to teleport back to Commit #3.

Who & When: Every save point records the author's name, email, and exact second.
What Changed (Diff): Shows exact green (+) added lines and red (-) removed lines.
Time Travel: Jump back to any previous commit hash (`27ef652`) anytime.
05 / Clearing the #1 Confusion Slide 6 / 24

Git vs. GitHub vs. GitHub Desktop

Beginners often use these names interchangeably, but they are three distinct layers working together:

1. The Local Engine

Git (On Your Laptop)

Created in 2005 by Linus Torvalds (creator of the Linux kernel). It lives on your computer, tracks changes inside a hidden .git folder, and works 100% offline without internet.

Interface: Command Line (git commit)
2. The Cloud Website

GitHub.com (In the Cloud)

Founded in 2008. A web platform that hosts your Git repositories online so teammates can clone your project, open Pull Requests, review code, and track issues.

Analogy: The Cloud Multiplayer Lobby
3. The Visual GUI

GitHub Desktop (GUI App)

A friendly visual app installed on your PC. Instead of memorizing terminal commands on Day 1, you click visual buttons—and every button runs the exact same Git command underneath!

Today: We learn Desktop + CLI side-by-side!
06 / Developer Dictionary Slide 7 / 24

Speak Like an Engineer: 9 Core Terms

Master these 9 words and you will understand 95% of every Git conversation in school and industry:

1. Repository (Repo)

A project folder tracked by Git, containing all your files plus their complete revision history.

2. Working Directory

The actual files you see and edit in VS Code right now before saving them into Git history.

3. Staging Area (Index)

The "loading dock" or shopping cart where you check-mark which modified files go into your next commit.

4. Commit (Snapshot)

A permanent, named save point in your local history with a unique ID hash (e.g., 4aa3630).

5. Branch

An isolated parallel timeline (widget/juan) where you build features safely without breaking main.

6. Remote (`origin`)

The version of your repository hosted on GitHub's cloud servers. By default, Git nicknames it origin.

7. Clone vs. Pull

Clone downloads a repo for the very first time. Pull downloads new updates into an already-cloned repo.

8. Push

Uploading your local commits from your laptop up to the origin repository on GitHub.

9. Pull Request (PR)

A request on GitHub asking the team to review your branch and merge your new code into main.

10 / Security & Hygiene Slide 11 / 24

Why .gitignore Exists: Never Commit Secrets or Junk

Not every file in your project folder belongs on GitHub. The .gitignore file tells Git which files to make completely invisible to git status and git add:

class-hub/.gitignore 4 lines
node_modules/ 100MB+ auto-installed packages
.env API keys, DB passwords, secrets!
.DS_Store macOS hidden folder metadata
Thumbs.db Windows hidden icon cache

Real-World Horror Story: Leaked `.env` Keys

Automated hacker bots scan public GitHub commits within 3 seconds of a push looking for OpenAI, AWS, Firebase, or GCash API keys. Once pushed, even deleting the file leaves the key in your commit history!

Good Engineering Habit

Always check that .env and build folders (dist/, node_modules/, __pycache__/) are listed in .gitignore before your first commit.

Inspect every green line in the Changes tab. If you cannot explain what a change does, ask the AI to explain it—or do not commit it!

One prompt → test in browser → one working change → one commit. Never dump 5 unrelated changes into a single giant commit.

Keep all widget logic inside widgets/yourname.js. No external libraries, no changing style.css, and never paste API keys.

Why Merge Conflicts Happen (And Why They Aren't Errors!)

        

          Why did merging Student #1's PR suddenly cause a conflict on Student #2's branch? Because both of you edited the exact same lines under the comments in index.html and README.md!
        


        

          
          

            

              
 Git Refuses to Guess (And Delete Code)

              

                Instead of silently overwriting Maria's widget with Juan's widget, Git pauses the merge and inserts 3 Conflict Marker Lines so a human can decide how to keep both.
              

            


            

              
Anatomy of Conflict Markers (`CHEATSHEET.md`):

              
<<<<<<< HEAD (Your branch's version)

              
<script src="widgets/juan.js"></script>

              
======= (Divider between the two versions)

              
<script src="widgets/maria.js"></script>

              
>>>>>>> main (Incoming version from main)

            

          


          
          

            
How to Resolve in 4 Calm Steps:

            
    
              
  1. Trigger Update: On your branch in GitHub Desktop, click Branch → Update from main (git merge main).
    2. 
              
  2. Open in Editor: When Desktop reports a conflict in index.html or README.md, click Open in Visual Studio Code.
    3. 
              
  3. Keep BOTH Widgets & Delete Markers: Keep both students' <section> tags, <script> tags, and README.md names, and delete the 3 marker lines (<<<<<<<, =======, >>>>>>>).
    4. 
              
  4. Test, Commit & Push: Save the file, reload index.html in your browser to confirm both widgets work, then click Continue merge → Push origin!

          22 / Phase 5: Time Travel & Recovery (2:35–2:55)
          Slide 23 / 24
        

        
When AI Breaks Your Code: restore vs. revert

        

          Ask AI to "Make my widget 10x fancier" and paste it over your file. If it breaks, how you undo depends on whether you committed yet:
        


        

          
          

            

              SCENARIO A: UNCOMMITTED MESS
              git restore <file>
            

            
1. Discard Uncommitted Changes

            

              You saved a broken AI edit in VS Code, but haven't clicked Commit yet.
              
In Desktop: Go to Changes tab → Right-click file → Discard changes... Instantly restores the file to your last commit!
            

          


          
          

            

              SCENARIO B: ALREADY COMMITTED MESS
              git revert <commit>
            

            
2. Safely Revert a Bad Commit

            

              You already committed (or pushed) the broken change.
              
In Desktop: Go to History tab → Right-click the bad commit → Revert changes in commit. Creates a brand-new undo commit so history stays honest!

Quick Self-Check Exit Ticket (Click to Reveal)

              

                

                  1. What is the difference between Commit and Push?
                  
Commit saves a snapshot locally on your laptop (offline). Push uploads your local commits to GitHub (origin) so the team can see them.

                

                

                  2. Why do we use branches instead of `main`?
                  
Branches isolate your work (widget/yourname) so you can build and experiment without breaking the working main branch for your teammates.

                

                

                  3. What does a Pull Request give a team?
                  
A PR gives the team a place to inspect the diff (Files changed), leave code review comments, catch bugs, and resolve conflicts before merging into main.

                

                

                  4. What do you do if AI breaks your code?
                  
If uncommitted: Right-click → Discard changes (git restore). If already committed: History → Right-click → Revert (git revert).
